# 02 — Artifact anatomy and signature analysis

## 1. Container

The ZIP at the repository root is an XAPK v2 bundle. Its own comment is
`ApkPure.com`; the inner APKs carry **no** ZIP comment, no data descriptors
(general-purpose flag bit 3 clear for all 6,162 base entries) and no gaps between
local headers — i.e. the archive is contiguous and machine-generated by
`apksigner`/`zipalign`, not re-zipped by a human.

| Member | Bytes | Kind | Role |
|---|---|---|---|
| `vn.com.vng.zalopay.apk` | 79,359,087 | base | manifest, DEX, resources, assets |
| `config.armeabi_v7a.apk` | 24,828,408 | ABI split | all 27 `.so` payloads |
| `config.xhdpi.apk` | 1,232,563 | density split | xxhdpi drawables |
| `config.vi.apk` | 86,425 | language split | Vietnamese overrides |
| `config.en.apk` | 74,137 | language split | English overrides |

The base manifest declares `requiredSplitTypes="base__abi,base__density"` and
`splits0.xml` enumerates the language splits, so the bundle is internally
consistent. The base APK alone expands to **136.4 MB** — 1.7× its compressed
size — which is why in-memory analysis on constrained runners needs care.

## 2. Signature block layout

`findSigningBlock()` locates the block through its trailing magic and length
field. The block is exactly 8,192 bytes (page aligned), and the central directory
starts at `0x4b2a000`, also exactly page aligned:

| Pair | ID | Size (B) | Content |
|---|---|---|---|
| v2 | `0x7109871a` | 1,383 | 1 signer, 1 digest (SHA-256), 1 cert, 1 signature |
| v3 | `0xf05368c0` | 1,383 | 1 signer, minSdk 24, maxSdk 2147483647 |
| source-stamp | `0x6dff800d` | 3,061 | Play source-stamp lineage |
| play-frosting | `0x2146444e` | 691 | Play "frosting" attribute |
| padding | `0x42726577` | 1,602 | alignment padding |

Both v2 and v3 record the **same** content digest. v3 adds SDK targeting, which
is how Android selects a signer during key rotation (only one signer here).

## 3. Verified facts

* Algorithm: `RSASSA-PKCS1-v1_5-SHA256` (`0x0103`), 256-byte signature.
* Signer certificate: self-signed, RSA-2048, `CN=Vu Manh Hieu`,
  serial `153EA9FD`, validity `2016-04-21 → 2041-04-15`,
  SHA-256 `59dd31fdf36070a0d7f8c8cde843fac371df7f1a915c0136c9c9b55992e8cdae`.
* No v1 (JAR) signature files exist in `META-INF/` — normal for `minSdk 26`.
* Signature verification over the signed-data block: **true for all five APKs**
  (cryptographic verification with the embedded SPKI public key).

A self-signed 25-year certificate with a personal common name is the classic
profile of a 2016-era Android release key kept in service. It matters for
analysis in two ways: (a) the identity is stable across versions, so the
certificate digest is a useful *pin* for tracking the app across distribution
channels; (b) any unofficial rebuild carrying user data would not verify.

## 4. Open question R1 — content digest not reproduced

The v2/v3 "signed data" records a 32-byte SHA-256 content digest. We implement
the documented chunked construction:

```
chunk      = H(0xa5 || u32le(len) || bytes)
section    = H(0x5a || u32le(nchunks) || chunk_digest*)
content    = H(0x5a || u32le(3) || section_digest*)
sections   = [0, signingBlockOffset) ∪ [centralDirOffset, eocdOffset) ∪ [eocdOffset, EOF)
```

For this artefact the recomputation yields a *stable but different* value for
every split, while the signature over the signed data verifies. We tested nine
plausible boundary/prefix variants (including re-padded block sizes from 4 KiB to
200 KiB in 4 KiB steps, zeroed and rewritten EOCD offset fields, and section
merges) without a match.

Two hypotheses remain:

* **H1 (tooling).** Our implementation diverges from `apksig` in a detail we have
  not found; the artefact is intact. Supporting evidence: ZIP contiguity, absent
  data descriptors, consistent local/central sizes, page-aligned block, and a
  certificate whose validity predates the current bundling pipeline.
* **H2 (post-signing relayout).** The archive layout changed after signing in a
  way that only affects the EOCD offset field (e.g. re-padding of the signing
  block), leaving the signature valid but the content digest stale. This would be
  detectable by `apksigner verify` and by an on-device install.

We publish the reproduction rather than a conclusion, because the decisive
cross-check (`apksigner verify --verbose`) requires a JVM that this sandbox does
not provide. **This is the single most important follow-up experiment for anyone
extending this work.**

## 5. Why the certificate pin still matters

Regardless of R1, the signing block gives an analyst a cheap, offline way to
distinguish "official client" from "repack": compare
`sha256(signing certificate)` across channels and versions. Every figure in this
repository is tied to the digest above, so a reader can confirm they are looking
at the same bytes we did.
